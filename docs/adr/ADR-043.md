# ADR-043 — App layers are built in a builder VM from a manifest; the manifest carries the RUN list

**Status:** Proposed (2026-10-17). Measured on MINIS in the cu1 spike
(2026-10-16). The decisions below are the operator's rulings of 2026-10-16 and
2026-10-17 and the orchestrator's rulings relayed by him. Spike code:
`57f6a22` (`build/app-layer-vm.sh`, `build/layer-builder/guest.sh`), dev
scaffolding — see *Not yet implemented*.

**Depends on:** [ADR-020](ADR-020.md) (signed release; see its revision note of
2026-10-17), [ADR-021](ADR-021.md) (agent split, RUN whitelist),
[ADR-030](ADR-030.md) and [ADR-032](ADR-032.md) (tiers and their paths),
[ADR-038](ADR-038.md) (guest addressing), [ADR-041](ADR-041.md) (Windows
applications).

**Context:** `build/app-layer.sh` builds an app layer on the host: a thin
snapshot of `vm_tpl_foundation`, mounted on the host, `chroot apt-get install`,
frozen read-only. That path needs the host on the network and the host
mounting content that apt wrote. An installed KatMate host has no network by
design — networking exists only through netVM — so the path cannot be given to
a user, and users must be able to build their own layers (their own browser,
office, applications). The RUN whitelist is a compile-time constant in
`vm-agent`, copied into `katmate-launch` and compared by
`tools/check-run-whitelist`; a layer the release did not anticipate cannot run
anything.

**Decision:**

1. **Layers of kind `debian-manifest` are built inside a short-lived builder
   VM.** The builder boots from the read-only foundation and reaches the
   Debian mirror through netVM like any AppVM. The host does three things only:
   `lvcreate -s` of the foundation, attach the snapshot as the builder's
   target disk, and `lvchange --permission r` after a successful build. On a
   failed build the host removes the snapshot. **After the builder has written
   to a layer, the host never mounts it.** The layer is content produced by a
   networked VM.

2. **T2 metadata comes from the host's own inputs, never from the layer.**
   `<layer>.meta` records `KIND`, `MANIFEST_SHA256` (the hash of the host's
   canonical package list — the bytes written to the builder's data disk, not
   the manifest file, so a comment does not change a layer's identity),
   `FOUNDATION` (the foundation tag it was built on), the kernel key of
   ADR-032 §5, `RUN` (decision 5) and `BUILT_BY=builder-vm`. What the builder
   reports — package list, versions, resolver check, byte counts — arrives over
   the serial console, is untrusted, and goes to logs only, never into T2.

3. **The builder is its own profile, not a class.** It has a T3 unit template
   (`katmate-builder@.service`) and a T4 program
   (`/usr/lib/katmate/layer-builder/guest.sh`) delivered on a read-only disk.
   It has no T1 file and is not an instance: the user does not author
   builders, and `f(class, netvm, nic)` is unchanged. Its shape: foundation as
   read-only root, target disk RW, program disk RO, manifest on a RO ustar data
   disk (the cfgdisk pattern), **no vsock device**, results on the serial
   console only, `panic=-1`, 2 GiB / 2 vCPUs, a 60-minute timeout. Having no
   vsock device, it needs no CID. It holds one reserved netVM slot (06,
   recorded in [PARAMETERS.md](../PARAMETERS.md)); one build runs at a time.

4. **The builder's PID 1 is bash: `init=/usr/bin/bash /dev/vdc`.** No AppVM's
   PID 1 gains a root path: `katmate-init` is unchanged and a builder is a
   different VM, not a mode of one. The cost is that the builder configures its
   own address, route and resolver with `ip` in its program, a second
   implementation of what `katmate-init` does from `km.ip=`/`km.gw=`/`km.dns=`
   (ADR-038). The two change together. `--` must not appear in a microvm
   `-append` ([INVARIANTS.md](../INVARIANTS.md)).

5. **The RUN list is part of the manifest.** Each manifest names the binaries
   its layer may run (`run`), hard-coded per manifest; changing it means
   changing the manifest, which means a rebuild. The host is the authority:
   `katmate-launch` checks a RUN request against the `RUN` line of the layer's
   T2 meta, which the host wrote from the manifest. The guest's copy is written
   into the layer by the builder (`/etc/katmate/run-whitelist`); `vm-agent`
   reads it once at start, before it accepts a vsock connection, and refuses
   every RUN if it is missing or unreadable. The guest-side check sits inside
   the guest's own trust domain, so carrying it in the layer costs nothing. The
   compile-time `WHITELIST`, `katmate-launch`'s `RUN_WHITELIST` and
   `tools/check-run-whitelist` go, and a change to a list no longer needs a
   foundation rebuild — only a rebuild of that layer. ADR-021's *absent, not disabled* is
   untouched: `netvm-agent` still contains no RUN code.

6. **Manifests have one schema and two tiers; the path is the tier.** A
   manifest is a flat TOML file, one per layer: `kind`, `packages`, `run`, all
   required, none empty. Release manifests are T3 at
   `/usr/lib/katmate/layer/<name>.toml` (from `manifests/` in the repository);
   the user's are T1 at `/etc/katmate/layer/<name>.toml`, `root:root 0644`.
   Package names must match `^[a-z0-9][a-z0-9+.-]*$`, validated on the host
   before any snapshot. A T1 layer whose name equals a T3 one is **rejected at
   parse** — release names are reserved, and two sources for one name is this
   project's characteristic failure class.

7. **An instance's `manifest` names a layer, not an enum member.** For
   `class = app` the value must resolve to a frozen layer with a meta whose
   `KIND` is valid for the class; the closed enum in `katmate-generate-env`
   goes. A layer whose `FOUNDATION` differs from the installed foundation is
   **stale**: it is not started, and it is rebuilt from its manifest.

8. **A recipe's kind is bound to the VM class.** This ADR defines
   `debian-manifest`, valid for `class = app` only. **Windows is a separate VM
   class** (`class = win`, name reserved here), as Qubes treats its Windows
   qubes: its own parameter set, its own deploy and its own lifetime, defined by
   its own ADR together with its recipe kind `installer` (an ISO and `C:\ODT`,
   installed interactively in an isolated VM). **The isolation unit of a WinVM
   is the whole Windows OS, not an application**: Edge and Office in one WinVM
   share one domain — files, registry, profile and network policy. A WinVM's
   list of RemoteApp names is a launch list, not an isolation boundary.
   Separating Windows applications means separate WinVMs.

9. **User layers are the user's content, outside ADR-020.** They are built on
   the user's machine from the user's manifest, like data in `/home`.

10. **The default layers move to on-device builds, gated.** Direction ruled:
    the release ships the foundation, netVM, the kernels and the host binaries;
    the default layers (web, office, vault) are built on the device at first
    boot, once netVM is up, from the release's T3 manifests. The release signs
    the manifests (package names), not package versions; the packages' trust
    anchor is the Debian archive signature, which apt verifies inside the
    builder. No project component arrives over the network. **Until gate B1
    passes, the default layers ship prebuilt.** A lockfile pinned to
    `snapshot.debian.org` was weighed and rejected: it trades the on-device
    build's freshness (security updates) for version-level reproducibility, and
    the snapshot service is slow and rate-limited.

**Evidence** (cu1, MINIS, 2026-10-16; builder 2 GiB / 2 vCPUs; n = 1 unless
stated):

- Build wall time: web 109 s, office 91 s, vault 45 s; about four minutes for
  all three, about 375 MB downloaded. `apt-get install` dominates; builder boot
  3.5 s, freeze 0.1 s; `apt-get update` 4–40 s across runs, mirror-dependent.
- The builder-built web layer holds the same 316 packages as the host-built
  `vm_app_web`; 4 carry newer versions — Debian security updates since
  2026-10-06.
- A failed build (unknown package name): FAIL 0.1 s into `apt-get install`;
  the snapshot was removed and the slot and NETCFG withdrawn. Nothing was left
  behind but the failed unit's record.
- An instance on the builder-built layer and one on `vm_app_web` (H3): foot
  ~3.9 s, Firefox ESR ~5.5 s cold start, alike on both; the operator observed
  all five windows at MINIS's screen — dark theme, no errors or warnings,
  smooth.
- First builder boot with `init=/usr/bin/bash -- /dev/vdc`: no root disk,
  panic — QEMU microvm appends `virtio_mmio.device=` after `-append`, and the
  `--` handed it to bash. Dropping `--` fixed it.

**Not measured:** a build on the Cubi (gate B1); the final form of the
`MANIFEST_SHA256` path (changed after the last build; OPEN-PROBLEMS #69).

**Not yet implemented:** decisions 3 (the spike uses transient `systemd-run`
units, a static slot and a required `KMB_WORK`) and 10; OPEN-PROBLEMS #70.
Decisions 5, 6 and 7 are in the tree (cu2), tested on fixtures and in
vm-agent's unit tests on the developer machine, and not yet run on a host;
the builder does not yet write `/etc/katmate/run-whitelist` into a layer.

**Gates (Proposed → Accepted):**

- **B1** — the three default layers built on the Cubi through the builder;
  wall time per layer recorded.
- **B2** — the canonical `MANIFEST_SHA256` path executed and its value
  matched against a recomputation on the Acer.
- **B3** — a T1 manifest end to end: layer built, instance started, a
  listed binary runs; an unlisted one is refused by `katmate-launch` and, sent
  by hand, by `vm-agent`.
- **B4** — a layer recorded against a different `FOUNDATION` refuses to start.

**Consequences:**

- The host never needs network access or a package manager for guests, and
  never mounts guest-written content.
- Release size drops by the default layers once B1 passes; first boot takes
  minutes longer, and an offline install has no AppVMs until netVM has a
  network.
- `build/app-layer.sh` becomes a developer tool only, then goes once the
  default layers are built on device.
- ADR-032 gains two manifest locations (§1) and loses the closed `manifest`
  enum (§3); ADR-021's whitelist becomes data; ADR-014's customization path
  (`--from <manifest>`) gets its mechanism. Their revision notes of 2026-10-17
  say so.
