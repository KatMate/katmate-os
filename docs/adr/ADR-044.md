# ADR-044 — Windows domains: `class = win`, a standalone WinVM and its RDP gateway as one instance, deployed unattended from the user's media

**Status:** Proposed (2026-10-30). The decisions are the orchestrator's
proposals of 2026-10-30, accepted in full by the operator the same day
(decision 7 after a detailed explanation). Nothing is implemented; gates
WG1–WG7 below. The class stays **experimental and user opt-in**
([ADR-041](ADR-041.md)).

**Depends on:** [ADR-014](ADR-014.md) (AppVM domain model),
[ADR-026](ADR-026.md) (domain indicator), [ADR-027](ADR-027.md) (VMM
containment), [ADR-030](ADR-030.md) and [ADR-032](ADR-032.md) (tiers, key
sets, profiles), [ADR-033](ADR-033.md) (p2p links), [ADR-036](ADR-036.md)
(host base), [ADR-038](ADR-038.md) (guest addressing), [ADR-041](ADR-041.md)
(the gateway path), [ADR-043](ADR-043.md) (§8 reserves `class = win` and the
recipe kind `installer`; §3 the builder as a profile).

**Context:** ADR-041 accepted the RDP RemoteApp gateway path on the w2 spike;
ADR-043 §8 reserved `class = win` for a separate VM class with its own key
set, deploy and lifetime, and set its isolation unit: **the whole Windows OS,
not an application**. Everything in w1/w2 was made by hand: an interactive
install in a QEMU window on the host (`-display gtk`), virtio-win drivers,
stop through `qemu-ga`'s `guest-shutdown` over virtio-serial, an
administrator `rail` account, and a TOFU certificate store. None of it is a
product shape.

Two facts constrain the deploy. The installed host has no network by design,
and there is no guest-to-host file path (FILEGET/FILEPUT were removed on
2026-10-06). A Windows ISO downloaded inside an AppVM lives in that guest's
filesystem, which the host does not mount (ADR-043 §1). The user's Windows
medium therefore reaches the host only as a medium the user brings.

**Decision:**

1. **A Windows domain is one instance of `class = win`: a WinVM and its
   gateway.** One T1 file, `/etc/katmate/vm/win_<name>.toml`; instance names
   begin with `win_`, as AppVMs begin with `app_`. The gateway is a **derived
   profile with no T1 file**, as the builder is (ADR-043 §3): one gateway per
   WinVM (ADR-041 decision 1), named and configured from the WinVM's
   instance. Several Windows domains may exist, each with its own gateway.
   Separating Windows applications means separate domains (ADR-043 §8).

2. **Profiles.** ADR-030 §2's function widens:

   | `class` | `netvm` | `nic` | profile |
   |---|---|---|---|
   | `win` | `Some` | — | `win-routed` (q35 WinVM, 1:1 link and a netVM slot) |
   | `win` | `None` | — | `win-offline` (q35 WinVM, 1:1 link only) |

   Derived from a `win` instance, never from a T1 file of their own:
   `win-gateway` (microvm; the 1:1 link only, never a netVM slot) and
   `win-install` (one-shot deploy, decision 5). Units:
   `katmate-win-routed@`, `katmate-win-offline@`, `katmate-win-gw@`,
   `katmate-win-tpm@` (decision 7) and `katmate-win-install@`, each with the
   instance as `%i`. The gateway and TPM units are bound to the WinVM unit
   (`BindsTo=`): stopping the WinVM stops both; the gateway can restart alone
   without touching Windows. ADR-032 §6 applies: the generator derives the
   profile from T1 and fails if the unit asserts another. The user cannot
   select weaker containment.

3. **The key set for `class = win`** (ADR-032 §3 widens):

   | | `class = win` |
   |---|---|
   | Required | `class`, `cid`, `mem`, `vcpus`, `netvm`, `apps` |
   | Optional | `clipboard` (bool, default `false`) |
   | Forbidden | `manifest`, `persistence`, `identity`, `disposable`, `reset_on_shutdown`, `nic`, `provides_network` |

   `manifest` leaves the common set and becomes required for `app` and `sys`:
   a Windows domain has no layer. `cid` is the **gateway's** CID, which is the
   domain's vsock identity for the domain indicator (ADR-026, ADR-041
   decision 1); `katmate-alloc` assigns it at create. The WinVM has no vsock
   device. `mem` and `vcpus` are the WinVM's; the gateway's are T4
   constants. `netvm` is present and may be empty, as for `class = app`.
   `apps` is the domain's launch list (decision 12). `clipboard` is ADR-041
   decision 3's per-domain opt-in.

4. **Storage.** One persistent thin LV per domain, `vm_<instance>` (e.g.
   `vm_win_office`), holding the whole Windows install: **standalone** — no
   layer, no delta, no ephemeral or disposable form. Windows updates itself
   inside the domain. The size is chosen at create; discard reaches the thin
   pool. `katmate-vm delete` keeps the LV, `--purge` removes it, as for
   AppVM homes. The gateway runs on a delta over the gateway layer,
   `/var/lib/katmate/instances/<instance>.gw.qcow2`, **recreated at every
   start**, with no home LV: it holds no state of its own.

5. **Deploy is unattended, through `katmate-vm create --class win`, after
   installation.** The installer does not offer Windows. The host generates
   `autounattend.xml` from a T4 template and create's parameters, onto a
   small read-only answer disk: local accounts (decision 11), RDP on, the
   firewall admitting TCP 3389 only on the link adapter and only from the
   gateway's address, the RemoteApp allow-list from `apps`, the provisioned
   RDP certificate, no automatic restarts by Windows Update (ADR-041 item 13),
   `RealTimeIsUniversal=1` (item 12), and Office from the ODT medium when one
   is given. The `win-install` VM has **no display and no network**;
   Windows Setup's own reboots stay inside one QEMU process, and the answer
   file's last step powers off. QEMU's exit within the deploy timeout is
   success; anything else is failure, and the LV is removed. A display exists
   only as a development drop-in, never a field (ADR-030 §6's pattern). The
   recipe kind `installer` (ADR-043 §8) is realised as these deploy inputs,
   recorded in T2 (decision 6), not as a manifest file.

   **Known obstacle:** the UEFI loader of an unmodified Windows ISO waits for
   a key (*"Press any key to boot from CD or DVD"*), and no key path exists.
   Candidates: a firmware boot entry for the medium's no-prompt loader, or a
   remaster inside a helper VM. Never on the host. Measured in WG1.

6. **The user's media arrive as raw block devices.** The Windows ISO is
   written to a stick with `dd` (on another machine); the ODT folder, with
   Office already downloaded (`setup.exe /download`, because the install VM
   has no network), goes on a second stick formatted FAT, exFAT or NTFS. The
   host attaches both read-only to the `win-install` VM and **mounts
   nothing**. From the ISO device it reads only the ISO 9660 primary volume
   descriptor's volume size (two fixed-offset fields, bounded by the device
   size) and records the SHA-256 of that many bytes in T2; comparing it with
   Microsoft's published value is the user's, documented. Later, the shared
   storage volume (operator's direction of 2026-10-04) may become a second
   source.

7. **Firmware, Secure Boot and TPM, always.** The WinVM is q35 with OVMF's
   Secure Boot code and SMM on. Each domain gets its own VARS, copied at
   create from a **release artefact** template with Microsoft's keys
   enrolled — the 2011 and the 2023 CAs, since Microsoft is replacing the
   former; keeping the template current is this project's work. Windows
   writes its own `dbx` updates into the domain's VARS. TPM 2.0 is always
   present, with no T1 key, through **swtpm** in its own unit
   `katmate-win-tpm@<instance>`: its own system uid, `--seccomp
   action=kill`, a systemd sandbox (`PrivateNetwork=`,
   `ProtectSystem=strict`), state in `/var/lib/katmate/win/<instance>/tpm/`
   (`0700`, that uid), socket in `/run/katmate/win/<instance>/`. QEMU only
   relays TPM commands; libtpms parses them, so swtpm is new host-side
   attack surface — confined, unprivileged, and below a QEMU escape, which is
   root today (OPEN-PROBLEMS #17). The host base gains `swtpm`, `libtpms` and
   `edk2-ovmf` (ADR-036). **The vTPM is no hardware root of trust:** host
   root reads its state; the host is the TCB.

8. **Devices: inbox drivers only.** Emulated NVMe for the disk, e1000e for
   the link NIC and, on `win-routed`, the uplink NIC. No virtio-win, no guest
   agent, no VGA, no USB, no audio; `-display none -monitor none`; Hyper-V
   enlightenments; fixed PCI addresses for every device in every launch form
   (ADR-041 item 5); `-no-reboot` at run time (item 11; not in `win-install`).
   Should the inbox set fall short of w2's numbers (WG6), virtio with
   virtio-win is the fallback, and its source and licence need their own
   ruling.

9. **No host channel into Windows.** The WinVM has no vsock device, no
   `qemu-ga`, no monitor. **Readiness:** the gateway waits for TCP 3389 on
   its link. **Stop:** the host asks the gateway, which runs `shutdown /s /t
   0` without `/f` inside the domain over RDP, so that applications can ask
   to save (ADR-041 item 14, expected, measured in WG3); after
   `TimeoutStopSec` the unit's SIGTERM ends QEMU, a hard stop. A reboot
   started by Windows ends QEMU (`-no-reboot`) and is visible to the host
   (WG5).

10. **Network.** A 1:1 link between the gateway and the WinVM in ADR-033's
    form (an AF_UNIX datagram pair), its socket paths derived from the
    instance under `/run/katmate/link/<instance>/rdp/`, and the same fixed
    `/30` for every pair (gateway `.2`, Windows `.1`, as in w2): links are
    isolated, so pairs do not collide. A `win-routed` WinVM holds one netVM
    slot per run, taken as an `app-routed` AppVM takes one. The gateway never
    holds a slot and has no route beyond its link: katmate-init gains an
    address-only form, `km.ip=` without `km.gw=` and `km.dns=` (OPEN-PROBLEMS
    #60). The firewall scope of decision 5 is a configuration; WG4 observes
    reachability.

11. **Accounts and secrets.** `rail` is a **standard user**; it runs the
    RemoteApp sessions. A separate administrator account, whose password the
    user gives at create, serves maintenance; UAC appears in the RAIL window.
    No sudo-equivalent is given to the daily account (the operator's rule for
    AppVMs, 2026-10-16). At create the host generates `rail`'s password and
    the RDP server certificate (ADR-041 item 15) into
    `/var/lib/katmate/win/<instance>/` (root, `0700`). After a successful
    install the certificate's private key and the answer disk are deleted;
    the administrator password is never stored. At every start the gateway
    receives `rail`'s password and the pinned certificate fingerprint on its
    read-only config disk (the cfgdisk pattern), with the peer address,
    `apps`, `clipboard` and the keyboard layout.

12. **Launch path.** The host is the authority over `apps`: T1 entries of an
    alias and a Windows program path. Launcher entries are generated from
    them. A launch starts the domain's units if needed and sends `RUN
    <alias>` to the gateway's vm-agent. **The gateway's vm-agent reads its run
    list from its config disk, not from its layer** — a deviation from
    ADR-043 §5 for this profile only, and a small change to vm-agent; RUN
    carries no argument, and the protocol is unchanged. Inside Windows the
    RemoteApp allow-list stays on (ADR-041 item 1), written at deploy from
    `apps`; it is not an isolation boundary (ADR-043 §8). An application the
    user adds later needs a T1 edit and the user's own allow-list entry inside
    Windows, documented. Window titles carry the domain's instance name
    (`km.name=` on the gateway).

13. **The gateway image.** The FreeRDP SDL3 client is compiled from upstream
    at release time and is a signed release artefact (ADR-041 decision 2,
    item 16). The gateway layer ships prebuilt, as the default layers do,
    until ADR-043's gate B1 passes; then the builder builds it on the device
    from a release manifest plus the FreeRDP payload, a new read-only input
    to the builder, settled with its T3 form (cu6).

14. **Status of the class.** Experimental and user opt-in. OPEN-PROBLEMS #17
    (QEMU as root, C1) does not block the opt-in; it blocks leaving
    *experimental*.

**Evidence:** none new. Carried from w1 and w2 (ADR-041): the gateway path,
its cost and its channel set; Windows 11 IoT Enterprise LTSC with Office
LTSC 2024 under q35, OVMF and swtpm (w1, interactive install). Not measured
for any decision above: an unattended deploy, the inbox device set, Secure
Boot with enrolled keys, swtpm under its seccomp filter, the stop through the
gateway, the address-only link form, and a reachability check of 3389.

**Gates (Proposed → Accepted):** on MINIS, then the Cubi. Before WG5, the
read-only `ev2.ps1` at the next boot of `vm_win_w1` (OPEN-PROBLEMS #59).

- **WG1** — an unattended deploy from an unmodified Windows 11 ISO and an ODT
  medium, with no display and no network: the install VM powers off within
  the timeout; wall time recorded; the domain then starts and RDP answers on
  the link.
- **WG2** — Word launched from the host menu end to end: units started, RUN
  to the gateway, a RemoteApp window at the host titled with the domain;
  time from the click recorded.
- **WG3** — a stop with an unsaved document: what Windows and Word show
  through RAIL, whether saving works, and the timeout path ending in
  SIGTERM; the next boot's state recorded.
- **WG4** — TCP 3389 refused from the netVM side of the domain's slot
  (a reachability observation, closing ADR-041 decision 4's configuration
  claim).
- **WG5** — a reboot started by Windows ends the WinVM unit and the host
  records it; the gateway's behaviour observed (ADR-041 item 9).
- **WG6** — the inbox device set against w2: boot to RDP, Word cold start,
  CPU idle and during a 60 s scroll; Windows reports Secure Boot *On* and a
  TPM; swtpm not killed by its seccomp filter in normal use.
- **WG7** — WG1–WG3 repeated on the Cubi.

**Consequences:**

- ADR-030 §2 and ADR-032 §3 widen; their revision notes of 2026-10-30 say
  so. ADR-043 §8's *"installed interactively"* is replaced by decision 5, and
  §5 gains decision 12's exception; ADR-043's note of 2026-10-30. ADR-041's
  product items 1, 5 and 11–15 are decided here; its note of 2026-10-30.
- The release set gains the OVMF VARS template, the FreeRDP build and, until
  B1, the gateway layer. The host base gains `swtpm`, `libtpms`,
  `edk2-ovmf`.
- New host locations: `/var/lib/katmate/win/<instance>/` (VARS, TPM state,
  secrets, the deploy record) and `/run/katmate/win/<instance>/`.
  `/etc/katmate/vm/win_*.toml` is T1 like any instance file.
- `katmate-vm` gains `create`, `status` and `delete` for `class = win`;
  `provision` stays `class = app` only.
- A Windows ISO downloaded inside KatMate cannot reach the host until a
  shared volume exists; documented, a consequence of the design.
- A Windows domain is memory-heavy beside the 16 GB minimum (ADR-041's
  measurements; the WinVM's `mem` is the user's).
- w2's leftovers on MINIS (the gateway LVs, `vm_win_w1`, slot 05's
  reservation) stay until WG1 passes, then go.

**Alternatives considered:**

- **An interactive install**, as in w1. Rejected: it needs a display path
  for a q35 VM — QEMU as a Wayland client of the host (`-display gtk`), or a
  VNC relay to a viewer VM, a new mechanism.
- **A file on a medium mounted on the host**, including a copy from
  `KMRELEASE` at install time. Rejected for now: the host kernel would parse
  the user's filesystem.
- **`qemu-ga` for stop**, written one way from `ExecStop=` (w2: 4.0 s).
  Rejected: a host-to-guest channel ADR-030 §6 does not know, a component
  from virtio-win inside Windows, and a stop that does not wait for unsaved
  work.
- **virtio with virtio-win.** Kept as the fallback of decision 8.
- **No TPM** — IoT Enterprise LTSC only, or the unsupported LabConfig
  bypass. Rejected: the editions most users bring need TPM 2.0, an
  unsupported configuration may lose feature updates, and BitLocker on a
  headless VM would need input that has nowhere to come from.
- **The gateway as its own `class = app` instance with a T1 file.**
  Rejected: two sources for one domain, this project's characteristic
  failure class.
- **RUN with an argument naming the application.** Rejected: a protocol
  change for every vm-agent to serve one profile.
