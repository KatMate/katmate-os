# ADR-041 — Windows applications via an RDP RemoteApp gateway microVM

**Status:** Accepted (2026-10-15). Operator's ruling that the gateway path is
usable; the mechanism was measured in the w2 spike (2026-10-14/15). The
feature stays **experimental and user opt-in** (`ROADMAP.md` § *Windows
application windows via RDP RemoteApp*). Accepted is a decision, not an
implementation: no tracked file builds, launches or configures a gateway or a
Windows guest, and every product item below is recorded, not done.

**Depends on:** [ADR-014](ADR-014.md) (AppVM domain model),
[ADR-022](ADR-022.md) (network object model), [ADR-026](ADR-026.md) (domain
indicator), [ADR-033](ADR-033.md) (p2p links over AF_UNIX datagrams),
[ADR-038](ADR-038.md) (guest addressing).

**Context:** Windows applications are to appear as ordinary per-window
Wayland surfaces beside the other domains. KatMate ships the client side only;
the RDP server is the Windows guest's (the user's own licence), and the Windows
guest is an untrusted domain like any other. An RDP client parses data from
that untrusted server, so it does not belong in the host TCB. RemoteApp
(RAIL, MS-RDPERP) with FreeRDP's SDL3 client worked natively on Wayland on
2026-10-08 ([RAIL-TESTS](../RAIL-TESTS.md)); whether it works inside a
microVM, with its windows reaching the host through waypipe, and at what
cost, was unmeasured until w2.

**Decision:**

1. **One gateway microVM per Windows AppVM** (WinVM). The gateway runs the RDP
   client and nothing that reaches the host except waypipe; its RemoteApp
   windows reach the host compositor through the existing waypipe path. One
   gateway per WinVM makes the gateway's waypipe identity the Windows
   domain's identity for the domain indicator (ADR-026).
2. **The client is FreeRDP's SDL3 client (`sdl-freerdp`), built from upstream
   source** (a stable release, signature-checked against a pinned key) on the
   Debian foundation (trixie, ADR-002). Debian's `freerdp3` package and an
   Arch-built client are rejected (operator's ruling, 2026-10-13). Native
   Wayland, no X11 server in the gateway.
3. **Channel set by construction.** `rdpdr` and its device sub-channels
   (drive, printer, smartcard, serial, parallel), `urbdrc`, `audin` and
   `rdpsnd` are compiled out; clipboard is compiled in and off unless the
   user opts in per domain. The client explicitly switches off the three RDP8
   defaults that otherwise pull in `rdpdr`: NetworkAutoDetect,
   SupportHeartbeatPdu, SupportMultitransport (w2's H7 Proposal 1:
   `networkautodetect:i:0`, `bandwidthautodetect:i:0`, `-heartbeat
   -multitransport /network:auto`).
4. **Network shape.** The host has no IP path to the WinVM. The gateway
   reaches the WinVM only over a **1:1 link** (ADR-033 form), TCP 3389, with
   the WinVM's firewall admitting 3389 only on the link adapter, from the
   gateway's address. The WinVM may hold **one optional netVM slot** for its
   own uplink (operator's ruling, 2026-10-10: the WinVM gets internet through
   netVM). The firewall scope is a **configuration claim** from an in-guest
   read-back, not a reachability observation: TermService listens on every
   address, and nothing checked 3389 on the netVM slot from outside.

**Evidence (w2, on the build/runtime host, kernel `7.2.10-hardened1-1`; n = 1
unless stated):** The spike ran a gateway layer (foundation snapshot +
`foot` + FreeRDP 3.32.2 from upstream source, signature-checked, built in a
throwaway trixie chroot, SDL3 3.2.10 from trixie) against a Windows 11 Pro
guest with Office LTSC 2024, over a 1:1 link `10.200.0.2` ↔ `10.200.0.1`;
the WinVM also held netVM slot 05 (NETCFG 205).

- **Usable.** Word's RemoteApp window, with its own frame and no licence or
  sign-in dialog, appeared **≤ ~1 s** after the password Enter (hand
  stopwatch), **twice**. The operator judged a 30-page typing/scrolling run,
  Save As and New *"great"*, with nothing odd or off.
- **Cost, idle** (Word open on its start screen, 60 s): gateway QEMU 0.1 %,
  host waypipe 0.0 %, WinVM QEMU 7.1 % of one host CPU.
- **Cost, 60 s scroll:** gateway QEMU **34.1 %** of one core, an upper bound
  (it includes rdpgfx DEBUG logging, ~37 lines/s, and software rendering in
  the gateway, llvmpipe inferred); WinVM 17.7 %; waypipe ~1 %.
- **M8 verdict (operator's ruling, 2026-10-15):** accepted on the operator's
  judgement and the CPU bound (34.1 % ≤ 100 %). The comparison with a direct
  host client (baseline A) was not run and is optional; *"same as direct"* is
  not shown.
- **Windows boot to agent (M1a): 9.17 s**, origin corrected for
  `/proc/stat` btime's whole seconds (+0.536 s on that host boot).
- **Codec:** RDPGFX v10.7; Windows chose ClearCodec/Alpha/Progressive and
  never used H.264, although it was offered (w2 finding 25).
- **Channels observed at run time:** ainput, rdpgfx, disp; no rdpdr. The
  build configuration was not read back for this claim.
- **Stop:** `guest-shutdown` ended Windows in 4.0 s **without waiting** for
  an unsaved Word document.
- **Corrections to the earlier w1b spike** (its record is outside the
  repository): its M1 values carry the same btime origin error (< 1 s, not
  recoverable); its configuration claim for slot 05 did not hold for its
  headless runs (slot 05 sat on a different PCI instance); its UNVERIFIED
  *"whether `guest-shutdown` force-closes applications"* is answered by w2:
  Windows does not wait, applications end without saving.

**Open consideration, not a blocker:** the rendering path in the gateway —
llvmpipe (today), virtio-gpu, or a GL-free client. At the measured cost it
does not block the decision.

**Consequences — product items** (recorded, not implemented; w2 findings are
cited by the report's numbers):

1. `TSAppAllowList\fDisabledAllowList=1` lets RAIL launch any program (w2
   launched PowerShell with it); the product needs the allow-list on.
2. The gateway build does not link X11 (no `libx11-dev` at configure time, or
   an explicit option).
3. The desktop user must not be in the `disk` group; the installer checks and
   refuses ([open problem #63](../OPEN-PROBLEMS.md); SECURITY-MODEL gap 16).
4. No product unit sets `panic=`; a guest that panics at boot leaves its QEMU
   and unit running ([open problem #64](../OPEN-PROBLEMS.md)). Not
   Windows-specific.
5. A Windows guest needs fixed PCI addresses for **all** its devices in every
   launch form, or Windows moves its network configuration between adapters.
6. The gateway client switches off the three RDP8 defaults (Decision 3).
7. The gateway package list names SDL3's dlopen'd EGL/GLES/libdecor
   libraries explicitly; `ldd` does not show them, and without them SDL fails
   with *"Couldn't find matching render driver"* (w2 finding 23).
8. The gateway build sets `WITH_VERBOSE_WINPR_ASSERT=OFF`.
9. The server can end a RAIL session on its own (it did overnight, *"initiated
   by an administrative tool on the server"*); the gateway needs a defined
   behaviour: relaunch, or tell the user the window closed and why.
10. Whatever closed Word overnight is disabled or scheduled in the product
    image: updates outside the user's session (cause: [open problem
    #59](../OPEN-PROBLEMS.md)).
11. Windows guests get `-no-reboot` or a reboot watch, so a guest reboot is
    visible to the host (w2 finding 26).
12. Windows guests get `-rtc base=localtime` or `RealTimeIsUniversal=1` (the
    RTC skew itself is a hypothesis).
13. Windows Update restarts are controlled in the product image: no
    unattended restart while a RAIL session is open.
14. **Stopping a Windows AppVM ends all its applications without saving.**
    Documented behaviour, the user's responsibility for now; a graceful stop
    path is a later item.
15. **A provisioned server certificate replaces TOFU.** The installer gives
    the WinVM its own RDP certificate and pins its fingerprint in the gateway.
    Windows renews its self-signed RDP certificate on its own (known Windows
    behaviour, not observed in w2), which a TOFU store would then reject.
    FreeRDP 3.32.2's new-host TOFU path also prints *"has changed … Host key
    verification failed"* while storing the certificate (w2 finding 22).
16. **A reproducible gateway image build in `build/`**: release check against
    the pinned keyring, chroot build, the channel set of Decision 3. Not yet
    implemented; w2's build scripts are outside the repository.

Also carried: katmate-init has no link-only address form, so the gateway's
default route and resolver point at the WinVM ([open problem
#60](../OPEN-PROBLEMS.md)); accepted for the spike.
