# ADR-042 — KatMate install medium: own archiso profile, offline package repository, release kept separate

**Status:** Proposed (2026-10-16). Measured in QEMU on MINIS (iso1 spike,
2026-10-16); accepted after an end-to-end install from a tagged release on
the Cubi. The decisions below are the operator's and the orchestrator's
rulings of 2026-10-16. Code: `01026ac` (`build/iso.sh`, `iso/`,
`installer/lib/packages.sh`).

**Depends on:** [ADR-006](ADR-006.md) (systemd-boot),
[ADR-020](ADR-020.md) (signed release, nothing built at install; see its
revision note of 2026-10-16), [ADR-040](ADR-040.md) (IOMMU kernel
parameters).

**Context:** Until iso1 the installer ran on the stock Arch live ISO. That
needed a network for pacstrap and for the keyring refresh, and the Intel
IOMMU parameter had to be typed into the boot entry by hand. ADR-020 left open
*"whether the installer needs any network at all (offline install as the
target)"*. Since the rulings R2, R3 and U1 of 2026-10-05 the release is a flat
set of files (`installer/lib/release.sh`), not an ISO carrying the images as
ADR-020 first said. iso1 built a medium for that release and measured it in
QEMU.

**Decision:**

1. **Own archiso profile in `iso/`, derived from releng** (archiso 91),
   built by `build/iso.sh` on an Arch host from the release tag's archive
   alone. Baseline is rejected: it is a cloud/VM image (cloud-init,
   hypervisor guest tools, sshd with root login) with no keyring
   initialisation and no autologin (iso1 H1.0).
2. **Guest images are not on the medium.** The release stays a separate
   flat-file set. The installer finds it on a filesystem labelled
   **`KMRELEASE`** (release files at its root) without asking;
   `KM_RELEASE_SRC` overrides; more than one such filesystem → refuse; none
   → prompt, with a default URL pinned to the medium's tag (never
   `latest`). A disk holding a `KMRELEASE` filesystem is never an install
   target (install.sh and preflight.sh). The release source is resolved
   **before** the network step, and on the medium a local release needs no
   network.
3. **The installer tree on the medium is the release tag's archive**,
   carried as the archive and unpacked at boot by `katmate-install`, because
   mkarchiso copies airootfs without file modes (iso1 H2.1).
   `rel_check_tree` compares that tree with the signed archive of the release
   it finds, so a medium and a release of different tags refuse each other.
4. **Offline package repository in the squashfs:** the dependency closure of
   `installer/lib/packages.sh` plus both microcode packages, with Arch's own
   `core.db` / `extra.db` from the resolving run. No locally built, unsigned
   database; package signatures are required
   (`SigLevel = Required DatabaseOptional`). On the medium the keyring refresh
   (`pacman -Syy`, `archlinux-keyring`) is skipped.
5. **Validity window.** `ISO_VALID_UNTIL` is the UTC date of the earliest
   expiry among the keys that sign the repository's packages. `build/iso.sh`
   refuses a build with fewer than 60 days left, and checks that the live
   keyring is byte-identical to the one it computed from. `install.sh`
   refuses on and after that date, before any question or disk access; there
   is no override. Rejected: `faked-system-time`, or any other change to gpg
   or keyring behaviour.
6. **Live system:** UEFI only (systemd-boot), squashfs/xz, one boot entry
   with `intel_iommu=on` (its effect on AMD hardware is not measured).
   Network firmware only (`linux-firmware-{intel,realtek,atheros,mediatek,broadcom}`);
   the target gets the full `linux-firmware` from the repository. Root
   autologin on tty1 with a 5 s launcher (any key → shell); empty root
   password on tty2–6, as on the Arch ISO.
7. **Signing:** the ISO is covered by the release key (ADR-020) as a
   detached signature, listed in `SHA256SUMS`. **Not yet implemented** in the
   release process ([open problem #67](../OPEN-PROBLEMS.md)).

**Evidence** (iso1, QEMU on MINIS, 2026-10-16; n = 1 unless stated):

| Measure | Value | Source |
|---|---|---|
| ISO size | 2 009 116 672 B, under the 2 GiB GitHub asset limit by 132 MiB (2 466 103 296 B before the firmware cut) | H3.0, H2.0 |
| Build time | 509 s | H3.0 |
| Offline repository | 571 packages, 1.21 GB | H2.0, H3.0 |
| Boot to installer prompt | ≤ 26.5 s from QEMU start, the launcher's 5 s included | H2.0 |
| Release autodetection, signature | `KMRELEASE` found, mounted read-only, network skipped; `SHA256SUMS: good signature` | H2.0, H3.2 |
| Offline pacstrap, real clock | exit 0, 31–33 s, 570 packages (n = 2) | H2.0, H3.0 |
| Offline pacstrap, clock +1 year | fails: `required key missing from keyring` (pacman's wording for an expired key) | H2.0 |
| `ISO_VALID_UNTIL` | 2026-12-31 for the 2026-10-16 build | H3.0 |
| Run with the clock at 2027-01-01 | refused before the first question; target disk sha256 and mtime unchanged | H3.2 |

**Not measured** (iso1 H2.6, H3.5): install.sh's own offline pacstrap line
(the runs above used the same arguments by hand, because `rel_check_tree`
refused the alpha2 release first); the URL path and Wi-Fi; the
multiple-`KMRELEASE` and release-as-target refusals; preflight's
`release-medium` record; real hardware, and whether the live firmware covers
the Cubi's NIC and Wi-Fi. One entry, closed by the Cubi gate:
[open problem #68](../OPEN-PROBLEMS.md).

**Consequences:**

- [`docs/INSTALL.md`](../INSTALL.md) describes the medium as the install
  path; the stock Arch ISO stays as the fallback.
- A medium lives until `ISO_VALID_UNTIL`, so a release medium is rebuilt
  before it, and its build date is bounded by the keyring: with today's
  keyring every build from about 2026-11-01 is refused
  ([open problem #66](../OPEN-PROBLEMS.md)).
- The ISO's margin under the 2 GiB asset limit is 132 MiB; `build/iso.sh`
  prints the comparison on every build.
- Also carried: install.sh's unguarded IOMMU-group glob
  ([open problem #65](../OPEN-PROBLEMS.md)), seen while reading for iso1.

**Revision note (2026-10-23, § *Decision* 5 and 7; rel1, `3c32a76`,
`3b4a80d`):** Decision 7 is implemented. Its "detached signature" is
`SHA256SUMS.asc`: the ISO is a release file listed in the signed `SHA256SUMS`
and carries no signature of its own, so the two commands of
[`docs/INSTALL.md`](../INSTALL.md) verify it with the rest. `build/iso.sh`'s
`.sha256` stays a build-host sidecar, not a release asset.
`tools/make-release.sh` requires `--archive` and `--iso` and binds the medium
to the release before it reads any image, from the ISO itself: its name, the
tag in `iso.env`, at least 60 days to `ISO_VALID_UNTIL` (Decision 5 applied
again at release time, counted to 00:00 UTC of that date), an embedded
archive byte-identical to `--archive`, and the ISO against its `.sha256`.
Those refusals were observed on MINIS; the copy into the release set and the
signing are not yet run ([open problem #67](../OPEN-PROBLEMS.md)). With
today's keyring the last day a release run accepts a medium is 2026-10-31 UTC
([open problem #66](../OPEN-PROBLEMS.md)). Open problem #65 is closed by
`3b4a80d`: install.sh refuses a netVM card without an IOMMU group (observed
over a fake sysfs, not on hardware). The text above is not edited.
